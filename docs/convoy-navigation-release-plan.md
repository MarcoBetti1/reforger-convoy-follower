# Convoy navigation and release plan

Reconciled 2026-09-26 with the [revised development brief](convoy-development-brief.md) and [adaptive roadmap](convoy-development-reset.md). The brief supersedes the earlier bounded overnight scope. Dependable following is the foundation; complete assignment, individual commands, arrival, regrouping, return, and release polish remain development objectives. The documentation-only setup is complete and the user subsequently resumed the updated goal. The [validation record](convoy-validation-current.md) and historical [pause checkpoint](convoy-pause-2026-09-26.md) retain the evidence; preserve newer code and results.

## Decision on splitting the mod

The current packaging decision is one player-facing addon while developing clear internal contracts. Reconsider it as physical evidence and independent callers emerge. The driver controller mixes boarding, following, road targeting, stuck recovery, arrival, return parking, and radio state. Refactor or replace inadequate boundaries when comparative prototypes support it. A separate public driving dependency needs demonstrated physical behavior, a clean non-convoy caller, a versioned API, and a justified compatibility/installation burden. Keep the generic harness independent throughout.

The convoy contract remains: Unit 1 follows the player's vehicle, each later unit follows its immediate predecessor, and only the leader reports convoy status to the owner. Navigation may change how a unit reaches a target, but it must preserve this chain and server authority.

The stateless road-polyline walk has already been extracted into `CF_RoadPolyline`, called by the controller: selected road points, lead projection, direction, and distance produce an interpolated point or failure. Separately, `CF_DrivenRoute` passed 25 native geometry cases but is not connected to production physical driving. Preserve these building blocks and their tests while comparing physical adapters; neither is a reason to retain an inadequate architecture unchanged.

The internal helper also has a forward-corridor clearance calculation. It measures exact road segments and the truck's short connection to the centerline, with the existing 8 m obstacle margin enforced by the controller. The reason for testing it was the road 81 v4 second release: the first truck parked and its successor reached the bay, but the approach-vector lane test rejected the same parked lead. Eighteen fixed native geometry cases cover road walking, bends, reverse direction, a diagonal bay approach, a genuinely blocked lane, and invalid roads. The later live blocked-lane control passed with the driver seated and 0.033 m motion. The larger multi-truck sequence remains unproved; geometry and a safe refusal do not establish successful arrival/return.

## Evidence before changing driving

1. Preserve the current packaged checkpoint and prior one-, two-, and three-follower road references. Resume with the specific hold and radius comparisons in the pause note, then refresh relevant baselines when changes require it. Counts exclude the player's vehicle; the existing hard cap is five recruited driver vehicles. Record world, pack hash, effective settings, mode, GAME transition, physical progress, gaps, target identity, native activity, waiting reason, and full video. GAME and a provisional terminal marker are not gameplay acceptance.
2. Reproduce one failure at a time: a tight paved turn, a mapped dirt road, a genuinely off-road segment, an out-of-order truck, a stationary predecessor, a removed middle truck, and an owner stop/exit/reboard. An off-road pass needs measured time beyond the road edge and physical movement, not a road-adjacent waypoint.
3. Compare viable strategies under equivalent starts and lead speed: current targeting, predecessor-trail guidance, waypoint lifecycle/refresh policy, and native pacing are hypotheses, not a mandatory rewrite. Change one causal variable per controlled comparison. Resolve movement ownership, speed units, braking and reset semantics. Keep navigability and obstacle checks; a trail point alone is not proof that it is drivable.
4. Add failure reasons to authoritative diagnostics: intentional queue hold, blocked by predecessor, no connected route, off-road start, waypoint completed short, unexpected exit, and genuine nonprogress. Recovery must not send all trucks into the same maneuver at once.

The September 26 packed three-truck run is a useful baseline: all links reached an on-road ordered stop without a sustained stall; two trucks then parked ahead. Its full return test failed because the player-vehicle bypass was blocked. That is not evidence that the normal following algorithm needs a rewrite. The Everon dirt/off-road scene is still staging only.

## Test grounds

Keep existing Arland and Everon subscenes for final game integration. Add compact, versioned scenarios with a single purpose and fixed starts:

| Scenario | Gate |
| --- | --- |
| Straight paved road | 1/2/3 trucks keep order and finish without prolonged nonprogress. |
| Tight turn | Trailing trucks negotiate the same turn without shortcutting into an obstacle or reversing after a transient order inversion. |
| Dirt road | The route follows a fixture whose road surface is verified as dirt; log the fixture surface label, tire positions, speed, road distance, and goal progress. `BaseRoad` exposes width and points, not a surface classification. |
| Off-road field | Vehicles traverse a surveyed drivable area beyond the mapped road edge for a measured interval. |
| Stop and restart | Owner stops, exits, reboards, and resumes without losing assignments; hold and dismount remain distinct. |
| Middle-unit failure | Downstream target reconnects to the next surviving predecessor and reports one useful leader call. |
| Arrival and return | Two explicit forward parks, player lead physically passes, then an explicit resume moves the original three-unit chain. A narrow rear turn refuses safely. |

Extend coverage to temporary obstruction, lag, changed order, missing members, driver/vehicle loss, interrupted boarding, repeated commands, and walking/passenger/driving transitions. Recovery must remain interruptible and preserve assignments deliberately. Use varied starting conditions and sustained sessions. Require at least 30 seconds of settled hold with no more than 2 m drift and a restart for the current hold investigation; keep the 60 m short-course peak-gap threshold. Continue observation beyond provisional markers when later movement or lifecycle behavior can invalidate them.

Terrain labels require physical evidence: the historically named `ConvoyFollower_Arland_ClearField_Offroad_1Truck.ent` runs on an unmapped concrete taxiway. Report it as `--fixture arland --surface off-network`. Verify natural-material moving wheel contacts for dirt/grass claims from both vehicles in the one-follower case and relevant participants in larger cases. Visual surface, road-graph inclusion, and vehicle navigation support are separate properties.

First build these as small subscenes on verified road/terrain patches so they run through the same game mode and AI stack as the addon. In parallel, prototype an independent base-world driving course only if its road network, terrain collision, and vehicle navigation can be validated in Workbench. Do not replace real-map integration tests with a synthetic course. Bohemia documents [new base worlds and terrain](https://community.bistudio.com/wiki/Arma_Reforger%3AWorld_Editor%3A_Terrain_Preparation_Tutorial), [road generation](https://community.bistudio.com/wiki/Arma_Reforger%3AWorld_Editor%3A_Road_Generator), and the [road network API](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfaceRoadNetworkManager.html); the installed Workbench build is the authority for what actually runs here.

The first fast arrival fixture is a separate one- and two-truck subscene on Arland road 81. It starts the lead 60 m before the stop, with followers at fixed 20 m gaps, and frames both short legs with a fixed camera. Its intended scripted-owner steering/braking did not establish powered motion: later calibration showed controls overwritten before physics. These courses are held; use the working native AI lead for immediate comparisons. Revisit scripted control only after addressing ownership or establishing a different method. The intended checks are arrival, authoritative Hold in vehicle, Resume, and renewed movement, with no teleport, pull-off, or keyboard/menu claim. The native geometry survey measured all five starts/goals on the connected 8 m road, with zero centerline offset, at `.cache/workbench-gui-runs/2026-09-26T02-20-45-764Z-34040/console.log`; that survey did not prove driving.

Keep the existing road 81 three-truck sequence as the longer forward-parking integration test. In its September 26 v2 run, the three-truck approach passed, then a test-only lead teleport roughly 25 m to the shoulder triggered `ARRIVAL_RESUMED` before a release order. Later fixtures stage the lead before follower arrival. A short arrival pass must never be presented as evidence for this separate shoulder, release, parking, owner passing, and resume sequence.

The isolated Everon offroad fixture surveys a 60–100 m field route before starting its test pilot. It requires both vehicles to travel at least 40 m beyond the mapped road edge plus 8 m and records consecutive physical movement there. A rejected terrain/obstacle survey is a fixture-selection result, not a convoy failure. A surveyed route alone is not an offroad driving pass.

A standalone base-world course is a later research spike because it must also provide an [AI world and navigation mesh](https://community.bistudio.com/wiki/Arma_Reforger%3ANew_Terrain_Setup) plus a game mode and factions. First prove a minimal straight road and one truck in that world; add curves, dirt, obstacles, and convoy behaviors only after AI pathing works there. This avoids mistaking a missing world system for a navigation-code failure.

The existing Arland OpenRoad fixtures are a provisional dirt-road candidate. Their starts near `(1371,3330)`, `(1347,3331)`, and `(1327,3332)` are road-centered, and the route is connected to a goal near `(1530,3334)`; footage shows a pale two-rut surface. Before reusing their 1/2/3 passing runs as dirt-road evidence, inspect the underlying Road entity and material in Workbench, or verify the vehicle contact material with an installed API. A two-rut appearance alone is insufficient. If it is dirt, retain that real-map fixture and add a narrower 150 m one- and two-truck dirt gate with clear tire-level video; build a synthetic base-world course later only if a controlled comparison is still needed.

## Fast, honest test loop

1. Validate scripts and pack once. Give each run a new log and video path; record the pack hash and world name.
2. Use a frozen packed client for unattended, scripted road tests while source changes are prepared. Do not overwrite its `data.pak` while it runs.
3. Use the established authorized Workbench workflow for source-only and player-panel tests. Require actual scenario evidence after GAME, including sustained/post-marker observation, and close source Workbench before edits to avoid hot-reload contamination. Keep one live desktop owner.
4. Parse physical and authoritative states separately. A command is accepted only when server validation passes; completion needs measured movement/seat/spacing and a settled state. Keep videos for visual claims and logs for state claims.
5. Select regressions for the changed behavior from 1/2/3 straight, tight turn, stop/restart, verified dirt/grass, and parking courses, then retain the full matrix for a mature candidate. Promote changes only with physical evidence and relevant regression checks. Distinguish test-only fixes from production integration. Do not weaken thresholds to turn failures green; explain any evidence-based metric correction. Preserve and classify gameplay and shutdown errors separately, including errors without a reproduced vanilla baseline.

The road23 fixture showed why fixture assumptions need an early check: after a full three-truck approach passed, the shoulder stage missed an arbitrary 25 m proximity cutoff by 0.294 m and no convoy command ran. Record surveyed start/stop/shoulder distances up front, give tolerance to measurements that can drift as AI settles, and still enforce terrain, road connectivity, vehicle occupancy, and obstacle checks when the maneuver actually starts.

## Release and repository gates

Complete the player workflow through authoritative whole-convoy and individual commands, assignment correction, unloading, regrouping, and resumed/return travel. Test real panel opening/closing on foot and seated and restored human throttle/steering; passenger-owner fixtures do not prove those controls. Keep hold, temporary dismount/reboard, and dismissal distinct. Radio and UI must report the same actual state, with leader-only speech, stale-event cancellation, and restrained repetition.

Verify US/Soviet vehicles and cargo interactions, server settings and invalid overrides, cap enforcement, cross-player ownership rejection, stale/simultaneous commands, disconnect/reconnect, member loss, and world/session cleanup. Obtain a valid separate-client/dedicated test path for advertised multiplayer support, diagnosing the prior vanilla authentication failure separately. Measure bounded route/state memory and the costs of updates, replication, diagnostics, and audio under relevant server conditions.

Keep generic tools and lessons in the existing independent harness repository; keep convoy source, permitted assets, scenarios, reporters, and concise evidence records here. Sync validated increments under the prior authorization. Retain raw recordings, profiles, temporary packages, model weights, and credentials outside public Git. Preserve newer changes and optional audio assets.

For mature milestones, demonstrate ordinary gameplay. The final candidate requires a filmed real-map supply journey covering preparation, travel, commands, actual unloading, and resumed or return travel, with full post-action observation. Complete five-configuration validation, packaging, installation/player/server guidance, compatibility/support boundaries, provenance, release notes, and troubleshooting tied to that exact build. Prepare Workshop material; publication remains a separate action. Preserve a passing candidate and continue worthwhile work until core behavior is complete and polished. Remaining optional scope and concrete external limitations must be clearly identified, with an exact checkpoint if interrupted.
