# Convoy Follower release audit (2026-09-25)

Scope: player controls, server-owner settings, radio assets, and map-maker/Workshop handoff. This is a source and documentation review; it does not establish live vehicle behavior. The [automated smoke guide](convoy-automated-smoke.md) and captured video must supply gameplay evidence before a release claim.

## Release gates, in order

1. **Show the actual convoy in a repeatable live run.** The recorded one-, two-, and three-truck runs should show follower movement, traffic spacing, stopped arrival, and continued driving after an order change. A log state transition or a view from the front of the lead vehicle alone does not establish that followers kept moving. The driver's waypoint and chain code remains under active pathing work.
2. **Exercise the complete player control loop.** In the same final build, confirm Start, Add, stop/arrival, the M923A1 rear **Pull off and regroup** entry, one released truck physically clearing the unloading spot, the next truck closing in, and the return line rejoining after the player's homeward crossing. Try **Regroup convoy for return** and **Resume convoy following** as explicit recovery paths. Repeat a minimal rear-menu and road check with the Soviet driver and Ural. The current [map-maker quickstart](convoy-mapmaker-quickstart.md) describes these controls and marks their live limits.
3. **Check the radio in game.** The optional generated pack has two alternate phrasings for each of 33 active call positions, with a different first choice and subsequent alternation per event/unit. The original pack remains the default, so the extra wording is not heard unless `m_iVoicePack` is set to 1. Check generated playback, a rapid threshold crossing, urgent call priority, and server-side voice off in a real client session. The offline headless server test only proved that the JSON profile was parsed; see [server-profile smoke](convoy-server-profile-smoke.md).
4. **Make the public claim match tested vehicle coverage.** The boarding action can select a nearby empty wheeled vehicle, but the rear release/resume/return controls are on the M923A1 transport and standard-body Ural4320 transport cargo parts only. A map maker must place one-member driver groups. The release listing should state the actually tested coverage and provide the quickstart. The [Workshop preparation checklist](convoy-workshop-release.md) already limits its proposed description to proven functionality.

## Source audit

- `CF_ConvoySettings.c` reads packaged defaults and optional authoritative `$profile:ConvoyFollowerSettings.json` once, clamps the convoy to one through five units, and exposes voice enable, voice pack, routine chance, repeat spacing, vehicle search radius, and movement/recovery thresholds. There is no driver-facing voice toggle. The profile parse succeeded in an isolated offline headless run with `m_bVoiceEnabled=false` and `m_iVoicePack=1`; networked dedicated usage and audible muting remain unverified.
- `CF_RadioPlayerController.c` routes calls to the ordering player's owner RPC, suppresses routine repetition, keeps urgent reports ahead of routine queued calls, and alternates generated variants when pack 1 is selected. `CF_UnderFireMonitorComponent.c` emits one hit report per attack episode; it does not report near misses. The 66 generated WAVs, source license, hashes, and readback audit are in [generated voice notes](convoy-generated-voice.md). This is asset and script evidence, not an in-game playback test.
- `CF_ConvoySession.c` delegates routine leader calls through the configured chance and forwards numbered exception reports. `CF_AddConvoyAction.c`, `CF_AssignTruckAction.c`, and `CF_ReplaceLeaderAction.c` now refer to the configured vehicle search radius without hardcoding `35 m`. The actual server override is not replicated to clients, so a numeric client-side hint could be wrong. The addon README now documents the explicit **Regroup convoy for return** action along with the automatic drive-past trigger.
- **Remaining usability issue:** `CF_ResumeConvoyAction.CanBeShownScript` shows **Resume convoy following** for any owned front driver, even without an unload hold. Its client `CanBePerformedScript` has no client-readable hold condition and therefore can appear usable until the server declines it. This is lower priority than driving and the rear release test, but should be checked in a real client and then hidden or disabled accurately with replicated state. `CheckOnServerFirstScript` correctly keeps the authoritative decision on the server; Bohemia's [BaseUserAction API](https://community.bistudio.com/wikidata/external-data/arma-reforger/ArmaReforgerScriptAPIPublic/interfaceBaseUserAction.html) distinguishes visibility, performability, and server-first verification.
- **Return-line radio edge case:** the hit monitor can call `CF_ReportUnderFire` for a seated, identified truck in the parked return queue, but `CF_ConvoySession.OnDriverStatus` currently looks only in the active outbound roster before forwarding a call. A hit on a parked return truck can therefore be logged without being heard by the owner. This has been sent to the session editor for a narrow fix or an explicit documented limit.

## Public handoff

Bohemia's [mod publishing guide](https://community.bistudio.com/wiki/Arma_Reforger%3AMod_Publishing_Process) requires a working mod, a linked Bohemia account, Workshop metadata, at least one category, and rights to the bundled content. The [project setup guide](https://community.bistudio.com/wiki/Arma_Reforger%3AMod_Project_Setup) covers scenario dependencies. The source repo can be public independently of Workshop upload. The selected Workshop description must avoid promising autonomous cargo delivery, every wheeled vehicle, or a phone menu. Bohemia documents a [ScriptedUserAction menu pattern](https://community.bistudio.com/wiki/Arma_Reforger%3ACreating_a_User_Action) and [commanding-menu modding](https://community.bistudio.com/wiki/Arma_Reforger%3ACommanding_Menu_Modding), so a remote command UI is technically possible but is not in this build.

**Recommendation on the default voice:** Select pack 1 for the release candidate only after a live audition with the user or a captured playback check. It satisfies the request for more lines and varied wording while keeping one consistent leader timbre; pack 0 should remain available for the player's original recording. Until that audio check, describing the generated voice as an optional alternate is the accurate public claim.
