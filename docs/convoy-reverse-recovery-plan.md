# Bounded reverse recovery — next product change

September 26, 2026. Design only: no source change, build or run. Root owns live validation. Preserve the failed v2/v3/v4 evidence and the private v4 recovery-handoff correction.

## Decision and evidence

Prefer a reversible **local physical route cursor**, with a separate monotonic **high-water station**, while retaining the current owned native guide order. This addresses native reverse recovery during ordinary travel as well as local arrival movement. Do not reset the route epoch, erase the original join, expand the corridor, or manufacture movement credit.

In `.cache/client/runs/loaded-pair-trip-v4/logs/console.log`, Unit Two retained exact guide sequence2 and its original driver/truck/predecessor. Lines2605/2661 show cursor58.4027 unchanged while the native truck reversed; lines2640/2674 show gear0 and signed steps -0.864008/-3.25105 m. Line2687 at17:39:19.354 reports `route_state_4`. The 60 m spacing gate had already failed at line2684; recovery must not erase that failure. The v4 arrival-handoff patch had not run.

`CF_DrivenRoute.c:207–326` starts at the current segment, only increments the segment, and only raises progress. A backward pose therefore remains compared with the old segment's clamped endpoint; its reported cross-track distance can include distance traveled backward along earlier route segments. That is a concrete structural limitation. The log does not include every exact recorded route vertex, so a corrected local projection succeeding on the complete v4 trace remains unproved. A genuine lateral departure beyond the existing 5 m corridor must still fail.

## Small supported route change

- Keep ordinary `CF_DrivenRoute.Query` unchanged. Add an explicitly enabled physical backtracking path in `CF_TrailGuideRoute.QueryPhysical` (`Scripts/Game/Tests/CF_TrailGuideEntity.c:138`). The ordinary/default query regression remains strict.
- Maintain an actual segment/station separately from the monotonic maximum station ever physically acquired. Arc gap, local corridor, sampling, arrival/Resume readiness and lookahead use the **actual** station. The high-water value is historical evidence, never a substitute for the truck's current location or a new movement budget.
- For an already genuinely joined route, inspect the current segment and at most its immediately preceding segment per actual query; keep the existing immediately following segment rule for forward travel. No global nearest-segment search, skipping vertices, remote hairpin selection or original-entry shortcut. Repeated frame-by-frame queries may traverse several preceding segments only with separately proved actual motion each time.
- Require exact retained epoch and unchanged segment endpoints/stations, finite poses, a previous accepted physical pose, and continuously owned/selected observation. On the same segment, bound station change by the actual signed displacement projected onto its tangent and the measured displacement. Across the previous vertex, mirror the existing adjacent projection proof with reversed leg order/directions: require negative motion along the original route, both residuals inside the unchanged corridor, an admissible local turn, and the measured chord plus the same geometric residual correction. Do not simply authorize negative progress using the old unsigned budget.
- A failed query commits neither cursor nor reusable physical proof. Zero motion cannot move either station. Missing/pruned previous history, ambiguous local geometry, a multi-vertex step, discontinuous or unobserved motion, target/epoch mismatch, control loss and true off-corridor motion remain explicit failures. Pruning must protect the actual cursor, not merely the high-water value.
- `QueryPhysical` currently snapshots accepted context only when a future segment exists (`CF_TrailGuideEntity.c:180`); backward proof must also work from the last retained segment without inventing a future sample. Match retained absolute station/point identities across pruning rather than treating a shifted array index as proof of a different path. Keep proof invalidation on reset, ordinary Query, failure and lost ownership.

## Controller and observer impact

- Preserve the exact existing guide/activity/waypoint during bounded reversing; do not move the guide backward. `CF_SetGuideStation` already enforces monotonic guide station, recorded-only goals and a forward-facing target. Use actual local station in `CF_UpdateTrailGuide` and retained-arrival/Resume queries; report local station, high-water and a physically proved backtracking flag explicitly. A valid route position during reverse is not powered forward movement.
- Keep original predecessor/session/world/pilot/seat/epoch ownership and route-history limits. Existing per-frame measurement, physical gap and native-failure gates remain; do not clear an accumulated unexplained displacement merely to obtain a new proof context.
- `CF_OriginalTailGuideProbeComponent.c:228–234` currently rejects any progress regression. Extend readback (`CF_OriginalTailGuideReadback` and `CF_TestOrdinaryReadRoute`) with distinct local station/high-water and proof status. Preserve the high-water/recorded-end/epoch/join invariants, and admit local regression only through the new physical proof. Do not just remove `route_cursor_moved_backward`. Keep original per-activity signed-distance accumulation and separate fresh Resume evidence; reverse distance already subtracts from its continuous segment. Update the loaded-pair continuity metadata only as required by that explicit distinction.
- Geometry probe contracts `progress_never_rewinds` and `projection_reverse_high_water_not_rebased` describe the old/default mode. Keep them for that mode. Add focused opt-in cases: straight reverse across successive previous segments then forward; reverse across a rounded adjacent corner; zero/underreported motion; stale/failed-query context; final-segment reversal; pruning; and a nearby hairpin return leg that must remain unavailable. Check actual station and high-water separately, plus transactional failure. No new test framework is needed.

## Why not switch to real-predecessor following first?

The existing direct original-follow machinery can target the actual immediate predecessor, preserving the daisy chain. However, changing from guide to vehicle requires exact retirement and a new native lease/order, may cut across a bend or leave the recorded corridor, and cannot count as uninterrupted guide movement. `CF_CreateEntityFollow(..., "moving_follow")` currently routes tails back into the guide, so a fallback would require an explicit bounded mode, cancellation/timeout and new observer handling. Reacquisition would still need the local physical cursor proof above; a direct order cannot authorize a remote join or erase a real off-route failure. Defer this broader fallback unless bounded local tracking proves insufficient. If later used, expose it as degraded real-predecessor recovery and start fresh movement evidence when the guide is physically reacquired.
