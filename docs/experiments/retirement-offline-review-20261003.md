## What V86 established

`native-match-v86/retirement-injected-1` deliberately failed the exact executing head order (generation 2, handler 1) at world time 117667 ms, while the original head truck was powered: 1.63335 km/h and throttle 1. This is an assisted failure-state diagnostic, not uninterrupted navigation acceptance. The fixture then stopped the player lead through its existing private engine actions. It never privately braked or repositioned a follower.

Early public Resume was rejected. Immediate Hold was rejected because the public command requires the lead to be slow; a later Hold was accepted. After a 3.01635-second physical stable observation with 0.0213846 m maximum drift, public Resume was still refused at world time 122400 ms. The retained result is **FAIL quiescent_resume_refused**, with player-input release validity **INCOMPLETE**, not PASS. No post-Resume movement occurred, and zero orphan-powered samples in this run does not prove cancellation or automatic stopping generally.

The frozen V86 controller calls `CF_ObserveFailedMovementStop()` only from `CF_CompleteUnloadDeparture()`, not its frame loop. That call cannot establish `m_bFailedStopQuiescent` during this retirement test. Consequently the readiness predicate remains false and the candidate blocks Resume. This is a concrete implementation defect, not evidence that the native engine cannot retire an order. The head's `NATIVE_CRUISE_RELEASED reason=state_change` at log line 4787 also shows that the desired zero-speed cap was not retained at that transition. The old log lacks the ownership-refusal detail needed to attribute that release to a particular guard.

The V86 fixture separately had bookkeeping defects: first Hold rejection left its `hold` flag false despite the later accepted Hold, and it demanded acceptance of an immediate repeated Resume even though the public API deliberately returns false when Resume is already in progress. An executed activity read immediately after the first Resume can be NULL, so that read alone cannot establish a fresh generation.

## What V88 changes, and what remains unknown

The preserved V88 stable package was compiled and packed on 1.8.0.13; it was never run. Its data SHA-256 is `BBC7D35FA238E77341BC615857B0B5D8D01890236F846CF370542167E7B8F79A`. V88 puts the observer at the end of the controller frame loop. Before ordinary frame work it requests the existing native cruise writer's zero-speed cap only when the sealed original truck/pilot/group/session/predecessor/handler and action ownership still match. It preserves that cap across `state_change` only while the same ownership test succeeds. Other releases still delegate to the base implementation. Waypoint cleanup applies the cap before retiring the owned waypoint; stock related-activity cancellation remains the cancellation route. No synthetic path setter, direct physics stop, replacement vehicle or blind cancellation of an unrelated action was added.

The observer requires all of: exact stop ownership, retired old slot/activity, completed native request, empty vehicle path, absolute speed below 0.5 km/h, absolute throttle at most 0.05, and one second stable within 2 m. Its 500 ms receipts now include the first ownership-refusal reason, handler identity, cap, action states, native completion/path, controls and quiescence. Explicit Resume releases the failed-stop witness/cap only after this readiness check and old-slot retirement. Failure history remains recorded.

These are source-level statements. Runtime must still show whether the ownership guard accepts the legitimate retirement transition, whether native speed zero actually drains old powered motion, whether another release defeats it, and whether a new public Resume acquires a fresh valid order. The absence of the V86 observer explains why readiness could not be recorded; moving the observer does not prove that all these predicates will become true.

V88 defers Hold until the lead has stopped and tracks a later accepted Hold. Two remaining fixture corrections are needed **before freezing a new test contract**: (1) repeated Resume should be expected to refuse while an order is in progress, and must leave assignments, request count/generation and prior evidence unchanged; (2) observe a new executing lease after Resume, require its generation to exceed the retired generation, and credit powered samples only while each original follower has its correct current predecessor binding. Natural-failure lease generation must come from a retained witness or the actual failure record, not a fabricated value when the executed activity is already gone.
